# Deployment notes

No hosted deployment has occurred. Sites was preferred, but no Sites connector or publishing capability is exposed in this task. AppDeploy was not used. The current validation is a local full-stack production build, not a hosted preview.

For browser review, the repository includes `.devcontainer/devcontainer.json`. The [Codespaces launch link](https://codespaces.new/whtefox57-hash/adaptive-reading-app?ref=reading-studio-preview) creates a user-owned environment with Node 24, the production build, seed data, the API and an independent worker. Port 3000 opens in the browser; keep its visibility private. `.devcontainer/origin.sh` uses GitHub's documented Codespaces hostname variables to configure the exact forwarded HTTPS origin and secure cookies. The GitHub image tag exists, and startup/origin handling were validated locally. No fresh Codespace was created in this task. This review environment runs only while the Codespace is active and is not a continuously hosted service; data resides inside that Codespace and is lost when it is deleted.

A host must support Node 24, server-side execution, a persistent writable disk, and a continuously running worker or supported scheduled job. A static-only Sites publication cannot satisfy persistence, accounts and server scheduling. Use a private/unlisted staging project if a suitable Sites server/persistence integration becomes available. Do not publish a static client that points at loopback addresses.

The supplied Dockerfile is an alternative deployment artifact; its image build has not been run, and it is not a deployed service. Deploy the same image as a web process and as a worker process, sharing `/app/.runtime` on the **same persistent host/volume**. Run the worker command `node node_modules/tsx/dist/cli.mjs server/worker.ts`; it does not need browser access. For multiple machines, replace SQLite with a shared transactional database and migrate the locking/unique-key contract rather than pretending two independent disks synchronize.

Set DATABASE_PATH identically for web and worker, APP_ORIGIN to the external HTTPS origin, and COOKIE_SECURE=true. The web service binds 0.0.0.0 and supports PORT. Build with npm ci and npm run build, preserve included full source licenses, then run npm start. Supervise both services and restart on failure. Probe /api/health and verify the worker heartbeat advances; an open port alone does not verify scheduling.

Before inviting real users: choose durable backup/retention controls, connect email verification/password reset, independently review editorial fidelity and territorial distribution, and implement real delivery integrations if notifications are offered. Billing stays off. No domains, subscriptions or paid resources were purchased or activated.

Live AI requires an authorized server-side provider connection. The included OpenAI-compatible adapter supports source-grounded questions and optional single-section revisions, with structured references, exact quotation checks, quantity rejection, source hashes/windows, bounded response handling, usage metadata, and visible pending editorial review. It treats source text as untrusted data and exposes no tool capability. Configure MODEL_API_KEY securely, MODEL_API_BASE with an authorized HTTPS endpoint, and MODEL_NAME. The default is api.openai.com/v1 with gpt-4.1-mini; the draft declares the credential requirement for api.openai.com. Source model-processing permissions are rechecked before and after a request. Token costs remain unknown without configured pricing. No real provider response has been tested here; mocked adapter tests do not establish live readiness. Scheduled generation still uses prepared editorial editions. Independent editorial fidelity review is required before public release.

Verify a new hosted deployment with the acceptance suite against its actual URL and a real supervised worker. Fresh-task snapshot restoration, public hosting, notification delivery and live AI have not been verified by local tests.
